## 1. Executive Summary

VocalGrid's navigation today is page-per-resource: `/dashboard/tables/[id]` for a table, `/dashboard/base-lists/[id]` for a base list's raw entities, `/dashboard/library` for a master-detail index of Lists/Templates. Moving from one applied template to another on the same Base List (e.g. "Class A1 → Grades" to "Class A1 → Attendance") means a full route change, which unmounts the grid and any active voice/VAD session.

This feature introduces a single persistent workspace, structurally similar to Notion/Linear:

- **Left sidebar** — Workbench switcher + nested Group tree (reusing `12_groups_workbenches.md`'s existing implementation) with Base Lists as leaves, plus an "Unassigned Lists" bucket.
- **Top template bar** — tabs over every Table generated by applying a Column Template to the active Base List.
- **Center grid** — the existing `TableGridSection` / `DataTable` / `VoiceEntrySurface` stack, unchanged, swapped by prop rather than by route.

The Base List and Template rows never disappear or remount across a switch — only the fetched `columns`/`rows` and the active-cell pointer change. Voice and Smart Pointer contracts (`05_VOICE_PIPELINE.md`, `06_SMART_POINTER.md`) continue to hold per-table; this doc adds the missing cross-table transition contract (§5) that those docs assumed a page reload would provide for free.

## 2. Data Model — No Changes, One New Include

No schema changes. The key existing fact this feature leans on: **applying a Column Template to a Base List already produces a real `Table`** — `applyTemplateToBaseList` (`lib/server/services/base-list-service.ts:174`) creates a `Table` named `` `${baseList.name} - ${template.name}` `` with `baseListId` set, in the same transaction as the `BaseListTemplate` join row. So "the templates attached to a Base List" and "the Tables belonging to a Base List" are the same set, and the template bar is a tab bar over `baseList.tables` — each tab's value is a `tableId`, not a `templateId`. No new join-table traversal is needed at render time.

`GET /api/base-lists/:id` must additionally include `tables: { id, name, createdAt }` (see §6).

## 3. Route & Layout Structure

```
app/dashboard/workspace/layout.tsx   // AppHeader + WorkspaceSidebar + <main>
app/dashboard/workspace/page.tsx     // reads ?list=&table= from the URL, renders WorkspaceHeader + WorkspaceGrid
```

State lives in the URL — `?list=<baseListId>&table=<tableId>` — updated with `router.replace(..., { scroll: false })`. A shallow replace does not remount `app/dashboard/workspace/layout.tsx` or `page.tsx`, so:

- The sidebar's fetched tree and scroll position survive every list/template switch.
- TanStack Query's cache (`queryKeys.tables.detail(tableId)`) makes revisiting a previously-viewed template instant.
- Deep links (`/dashboard/workspace?list=X&table=Y`) and browser back/forward work without extra code.

Sidebar composition is lifted out of `app/dashboard/library/page.tsx` (which already implements a workbench `Select` + `GroupTreeRoot` for its own master-detail shell) into `components/workspace/WorkspaceSidebar.tsx`, shared by both Library and the workspace.

## 4. The Template Bar = Table Tabs

`components/workspace/WorkspaceHeader.tsx` renders the active Base List's name/description and a `Tabs` row where each `TabsTrigger` corresponds to one entry in `baseList.tables`. The visible label strips the `` `${baseList.name} - ` `` prefix `applyTemplateToBaseList` adds to the generated Table name, falling back to the raw name if the prefix isn't present (a user may have renamed the Table since).

Selecting a tab pushes `?table=<tableId>` — this is the entire "switch template" operation. No merge/diff logic runs; the grid just refetches and re-renders with the new Table's `columns`/`rows`, exactly as `13_ux_ia_redesign.md` Decision 4 (strict 1 Table : 1 applied-Template) already guarantees.

A Base List with zero applied templates shows an empty state with a CTA into the existing apply-template flow (`POST /api/base-lists/:id/apply-template`) rather than an empty grid.

## 5. Pointer & Voice Reset Contract

`06_SMART_POINTER.md` and `05_VOICE_PIPELINE.md` describe pointer/voice behavior *within* a table session; neither addresses what happens when the active table changes without a page reload, because until now that never happened — every table switch was a route change that remounted everything. Persistent-workspace switching makes three previously-implicit behaviors explicit:

1. **Pointer resets to (Row 0, Col 0), not null.** `ui-store.activeCell` is global and un-scoped to a table. On table switch it must be reseeded to the new table's first row / first non-base column (base columns are read-only, same rule `DataTable` already applies to clicks) so voice input is immediately usable, per this feature's requirement that the pointer "stays ready for voice input."
2. **Any in-flight voice session stops.** `useContinuousVoice`'s VAD `onSpeechEnd` callback closes over `tableId`/`tableSchema` at `startVAD()` time (`lib/client/hooks/voice/use-continuous-voice.ts`). Without an explicit stop, a chunk captured after switching tables would still POST against the *previous* `tableId`. `useVoicePipeline` must stop continuous mode and clean up the recorder whenever `tableId` changes or the surface unmounts.
3. **Confirmation/provisional state clears.** `pendingConfirmation`, `pendingBatchConfirmation`, and `provisionalFeedback` are meaningless once the table they refer to is gone; they must clear together with the pointer reset, as a single store action (`setActiveTable`) rather than piecemeal — this keeps "the workspace moved to a different table" as one owned transition instead of several call sites each partially resetting state.

`table-cell-store.ts`'s existing `loadedTableId` + 5-minute TTL scoping already handles cell-value cache correctness across a switch and needs no change.

## 6. API Additions

| Route | Change |
|---|---|
| `GET /api/base-lists/:id` | `include` gains `tables: { id, name, createdAt }`, ordered by `createdAt asc`. No new route — the workspace reuses `queryKeys.baseLists.detail(id)`. |

No other endpoints change. `GET /api/tables/:id` already returns everything `WorkspaceGrid` needs to derive `columns`/`rows` (`table.schema.columns`, with the legacy `baseList.schema` + relational-`table.columns` fallback already implemented in `app/dashboard/tables/[id]/page.tsx`, extracted verbatim to `lib/shared/utils/table-schema-derivation.ts`).

## 7. Rollout Phasing

1. Server: `tables` include on `getBaseListById`. Shared: schema-derivation + tab-label utils extracted, unit tested.
2. Client safety: `ui-store.setActiveTable`, `useActiveTable` pointer-seed hook, VAD-stop-on-switch in `useVoicePipeline`. Verified against the existing single-table pages first (no behavior change there — `tableId` never changes mid-session on those pages today, so this is a no-op there) before the workspace route exists to exercise the switching case.
3. Workspace shell: sidebar, header/tabs, grid — new route only, existing pages (`tables/[id]`, `base-lists/[id]`, `library`) untouched.
4. Entry points updated (`AppHeader` link, Library rows link into the workspace) once the workspace has parity.
5. Optional follow-up (separate change, not bundled here): redirect `tables/[id]` → the workspace equivalent URL.

## 8. Known Gaps / Non-Goals

Carried forward, not addressed by this feature:

- `Table.baseListId` remains nullable with no DB-level uniqueness enforcing the 1:1-per-template invariant — enforced only by application code in `applyTemplateToBaseList`.
- `BaseListTemplate.autoSync` is stored but never acted on (no propagation of template edits to already-applied Tables) — see `02_column_templates.md`.
- No `GET /api/groups` list route exists; group discovery is still workbench-tree-only (`12_groups_workbenches.md` §9).
